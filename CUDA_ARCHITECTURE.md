# CUDA Port Architecture For 5D Combined-CWS Classification

This document is the implementation target for porting the PALP geometry path to CUDA while keeping the existing C/PALP pipeline as the golden reference.

## Scope

The CUDA port targets classification of 5-dimensional minimal reflexive polytopes generated by combined weight systems. The current 183B-row six-weight dataset is the completed single-weight `[6]` case; combined-CWS work begins with descriptor-driven generation of structure IDs `2..47` and a general CWS schema.

The first production CUDA milestone is now a GPU-resident combined-CWS/IP generator. The row-based geometry and normal-form backend remains a correctness reference, but it is not the production hot path for combined-CWS generation.

## Hardware And Cluster Assumptions

- Discover GPU nodes with `sinfo` and allocate with `srun`/`sbatch`, targeting `n3*` for the 4x RTX 6000 server.
- Confirm exact GPU model, memory, driver, and CUDA runtime with `nvidia-smi` inside the SLURM allocation. The working expectation is 4x RTX 6000 with roughly 96 GB VRAM each, plus another node with several L40 GPUs.
- Do not require sudo. Prefer cluster modules; otherwise install user-local dependencies under `$HOME` with micromamba/conda or a Python virtual environment.
- Every benchmark log must capture node name, SLURM job ID, GPU model, driver/runtime versions, compiler versions, git commits, and command line.

## CPU Reference Boundary

The reference computation remains PALP:

1. Decode a general CWS with `nw <= 5`, `N <= 10`.
2. `Make_CWS_Points` enumerates lattice points.
3. `Find_Equations` computes vertices and facets.
4. `Sort_VL` gives deterministic vertex ordering.
5. `Make_Poly_Sym_NF` computes the GL(5,Z) normal form.
6. xxHash128 hashes the used normal-form matrix.

CUDA code must compare against this boundary at intermediate stages, not only at final hashes.

## Data Model

For the current combined-CWS generation phase there is no Parquet in the hot path. Parquet conversion is a compatibility/export step for older row-based classifier tools, not the format used between enumeration and IP filtering. GPU workers should keep descriptor state, selected weight pools, candidate CWS rows, point workspaces, and IP-filter state resident on device; the host only loads static pools, launches shards, and flushes large accepted-CWS chunks to disk.

Normal-form computation is deferred for this phase. Accepted IP CWS rows can be deduplicated and normal-formed in a post-processing pass after the GPU generator has reduced the descriptor search space.

When row materialization is needed for compatibility, combined CWS rows should use a schema equivalent to:


```text
schema_version: int32
structure_id: int16
profile_id: int16
nw: int8
N: int8
degree[5]: int32
weights[5][10]: int32
source_weight_ids[5]: int64 or string
selection_indices[5]: int32
metadata: point/facet/Hodge fields when available
```

The `[6]` single-weight path remains supported as compatibility data with `nw=1`, `N=6`.

## Production Kernel Stages

### Stage A: Descriptor Enumeration

- Copy the `2..47` dim-5 structure descriptors and selected weight pools to device memory once per worker.
- Partition descriptor tuple ranges by SLURM shard/GPU.
- Apply PALP's selection-order canonicalization, descriptor automorphism checks, and shared-prefix canonical checks on GPU.
- Construct candidate CWS rows on GPU; do not round-trip every candidate through host memory.

### Stage B: IP Filtering

- Fuse candidate construction, lattice-point generation, and IP/facet checks into device-resident kernels.
- Keep per-block/per-warp point and equation workspaces on device.
- Append accepted IP CWS rows to a large device output ring/buffer.
- Flush only full accepted-row chunks to host storage.

Current status: `cuda_dim5_cws_scan --ip-check` implements the first bounded
device-resident IP filter, and `--stream-ip` implements the first chunked
full-shard GPU IP path. The scanner constructs CWS rows on GPU, builds the CWS
lattice basis and lattice points on GPU, runs a 5D PALP-style integer
`IP_Check`, stores accepted CWS rows on GPU, and can flush accepted rows to a
text file. It still uses one serial thread per candidate and a fixed point cap,
but the persistent IP bookkeeping now lives in explicit reusable device scratch
instead of the CUDA thread stack. The production performance gap is now true
intra-candidate parallel point/equation work and compact accepted-output chunks.

### Stage C: Post-Processing

- Run normal forms, global deduplication, and collision audits after accepted CWS rows exist.
- The existing row-based CUDA/CPU classifier can be reused as the audit implementation until a fully batched NF post-processor is warranted.

## Row-Based Reference Kernel Stages

These stages describe the existing correctness backend, not the final generator hot path.

### Stage 1: Runtime And Batching

- One host worker per GPU.
- Each worker owns CUDA streams, pinned host staging buffers, and device memory pools.
- Use dynamic work queues, because point counts vary by orders of magnitude.
- Bucket CWS rows by expected point-count class where metadata is available.

### Stage 2: CWS-To-Points

- Port `Make_CWS_Points` first.
- Use one CWS per block or cooperative block group for small and medium cases.
- Use prefix sums and compaction for variable point counts.
- Route pathological large point-count rows to a low-concurrency workspace pool.

### Stage 3: Vertex And Facet Discovery

- Port dot-product scans from `Find_Equations`, especially `FE_Search_Bad_Eq`, `Search_New_Vertex`, and `New_Start_Vertex`.
- Store points and equations in structure-of-arrays form for coalesced reads.
- Use deterministic reductions for minima and incidence masks.
- Preserve 64-bit incidence behavior where PALP depends on up to 64 vertices.

### Stage 4: Normal Form

- Build the vertex matrix and vertex-pairing matrix on the device.
- Run the PALP VPM canonical permutation search and GL(5,Z) triangular normal
	form as exact CUDA device integer code.
- Keep exact integer arithmetic; no floating-point geometry decisions.

### Stage 5: Result Transfer And Dedup

- Transfer compact results: status, dimensions, counts, and normal-form matrix.
- Compute hash on CPU initially; optionally compute device-side hash later.
- CPU merge/checkpoint remains authoritative for counts and collision audits.

## Multi-GPU Scheduling

- Partition by structure ID and shard first, then dynamically rebalance by measured throughput.
- Use two or more streams per GPU to overlap H2D transfer, kernels, D2H transfer, and CPU dedup.
- Keep per-GPU batch sizes adaptive: RTX 6000 and L40 nodes may differ in memory, clocks, and compute capability.
- Checkpoint per SLURM array task and per GPU worker so failed jobs can resume without losing completed shards.

## Regression Gates

CUDA output is acceptable only when these checks pass:

1. CWS descriptor parsing and embedding match CPU fixtures.
2. Device lattice-point lists match CPU PALP after canonical sorting.
3. Device vertices/equations match CPU incidence and facet data.
4. Device normal-form matrices match CPU PALP exactly.
5. Final hashes and merged counts match CPU reference on the same corpus.
6. Full-normal-form collision audit passes inside each xxHash128 bucket for audit runs.

## Benchmark Plan

Benchmarks must report:

- CWS/s and unique polytopes/s.
- Points/s and equation-scan throughput.
- Per-stage timing: generation, points, equations, normal form, transfer, CPU dedup.
- GPU memory high-water mark and workspace bucket occupancy.
- 1/2/4 GPU scaling on the n3* node.
- Cross-node comparison with L40 hardware.
- Nsight Systems timeline for overlap and Nsight Compute metrics for hot kernels.

Publish speedups only together with the regression corpus hash and parity result.

## Immediate Implementation Order

1. Keep the recovered descriptor-driven PALP code as the mathematical source of truth for descriptor enumeration, canonicalization, and IP filtering.
2. Use the CUDA descriptor scanner to measure exact prefix-pruned pre-IP counts for all combined structures.
3. Extend the current bounded GPU-resident candidate construction and IP filter into a streaming shard worker for all 46 combined types.
4. Replace text accepted-row output with compact chunked host flush; keep Parquet out of the generation/IP hot path.
5. Parallelize point generation/equation scans within heavy candidates, then run normal form and global dedup as post-processing until the accepted-CWS volume justifies a dedicated GPU NF pipeline.

- Optional CMake CUDA build with `-DENABLE_CUDA=ON` in `src/classify/build-cuda`.

	including the new-vertex minimum evaluation and tie-break. The fast path scans
	the selected PALP candidate equation by value; an all-candidate batched scan is
	available for future large-row experiments but is gated because it slowed the

- CUDA construction of the normal-form VM/VPM matrices from device points,
	vertices, and facets.
- CUDA port of PALP's canonical VPM permutation search and GL(5,Z) triangular
	normal-form reduction. The CUDA NF path is mandatory once entered; failures

Not yet production-optimized:

- `Find_Equations` candidate-equation bookkeeping: `GLZ_Start_Simplex`,
	incidence-mask bookkeeping, and `Make_New_CEqs` still reuse PALP CPU code
	inside the row-based correctness backend. The new descriptor scanner IP path
	has a separate device-side 5D port, but it is serial per candidate.
- CPU-side xxHash/dedup/checkpoint merge remains authoritative.
- The generic scanner's IP path processes a bounded candidate buffer per launch;
	it does not yet stream arbitrary prefix-candidate chunks through a persistent
	device ring buffer.
- The accepted-row writer is currently text for measurement. Production should
	write compact chunks and avoid materializing rejected candidates.

Performance implication:

- The current CUDA backend is a correctness-complete geometry/NF port for the
	implemented stages, not the final fast production path. On small and medium
	combined-CWS rows it is slower than the CPU path because each CWS still pays
	several kernel launches, host synchronizations, point-list copies back to CPU,
	and PALP CPU candidate-equation bookkeeping.
- Nsight Systems on 64 structure-5 rows measured 1335 kernel launches, 1849
	`cudaMemcpyAsync` calls, and 1335 `cudaStreamSynchronize` calls. The GPU did
	only 86 ms of kernel work, with 64 canonical-NF launches taking 68.8 ms and
	1141 equation-scan launches taking 6.1 ms. The bottleneck is orchestration and
	device/host ping-pong around many tiny kernels.
- The next required optimization is a device-resident batched row kernel: many
	CWS rows per launch, persistent device point/equation workspaces, device
	incidence/candidate bookkeeping, and compact result transfer. Without that,
	more scalar ports of PALP helper routines will not reach the sustained rates
	needed for a `10^13` geometry-run classification.
- For the fixed type-3 path, enumeration is already fast enough on RTX 6000.
	The generic all-type descriptor scan likewise shows that enumeration and
	prefix canonicalization are not the production bottleneck: one GPU counted all
	46 combined structures in 3.72 min, and a sharded four-GPU run should be on the
	order of one minute for prefix counting.
	The remaining bottleneck is the GPU IP filter over the exact
	12140535288504 pre-IP candidate rows. The current streaming GPU IP path checks
	structure-12 samples at roughly 336k candidates/s/GPU, but interior type-3
	`(5,5)` samples reached only about 63k-161k candidates/s/GPU after launch
	tuning. Type 3 dominates the full count, so the current full generation+IP
	estimate is roughly 2.17-5.27 years on one GPU, 198-481 days on four ideal
	GPUs, or 99-241 days on eight ideal GPUs before true intra-candidate
	parallelization.
	The W5 selected pool is too large for CUDA shared memory, so it lives in
	persistent device global memory and uses the GPU caches; shared memory should
	be reserved for per-block/per-warp point/equation/IP workspaces. The next
	kernel should parallelize point generation and equation checks within each
	candidate, especially for type 3, and replace text accepted rows with compact
	chunks.

The CUDA backend now reports itself as
`cuda-points+equation-scans+canonical-nf`.
